# Правила для агента

Проект: игра «Накорми зверей» на Godot 4.7 (GDScript) для Яндекс Игр, веб-билд, в основном телефоны.

- Краткий план и список шагов: `docs/PLAN.md`.
- Планы: `docs/PLAN.md`, `docs/PLAN_WORLD.md`, `docs/PLAN_POLISH.md`, `docs/PLAN_RELEASE.md`. Шаги выпуска нового биома: `Выполни B<N> для биома <id>`, файлы в `docs/tasks/release/biome/`. Общие правила задач релиза: `docs/tasks/release/_RULES.md`.
- Подробные задачи: `docs/tasks/`.
- Справочники: `docs/reference/`.
- Нерешённые вопросы: `docs/OPEN_QUESTIONS.md`.
- Выполненные шаги и журнал: `docs/PROGRESS.md`.

## Главные правила

1. **Говори с пользователем только по-русски**: ответы, отчёты, вопросы, объяснения ошибок. Имена в коде на английском, комментарии в коде на русском.
2. **Не делай коммиты, пока пользователь не написал «фиксируй».** До этого слова никаких `git commit`, `git push`, `git reset`, `git stash`, веток и тегов. Когда он написал «фиксируй»:
   1. Проверить `git status`.
   2. Обновить `docs/PROGRESS.md`.
   3. Добавить через `git add` только файлы текущего этапа и `docs/PROGRESS.md`.
   4. Создать коммит с названием **дословно из `PROGRESS.md`** для этого шага. Перед коммитом в `PROGRESS.md` отметь «зафиксировано: да», этот файл входит в коммит.
   5. Выполнить `git push origin main`.
   6. Выполнить `git push origin2 main` (зеркало). При необходимости `--force` **только по отдельной просьбе пользователя** — используй и сообщи.
   7. Проверить `git status` и `git log origin/main..HEAD` для обоих remote.
   8. Сообщить пользователю хеш коммита и результат отправки в оба репозитория.
   При конфликте локальная версия должна перезаписывать удалённую версию в репозитории, при необходимости выполняй принудительный push и сообщи пользователю. Без слова «фиксируй» push не делай.
3. **Работай по одному шагу.** Пользователь пишет «Выполни T05» (номер шага из `PLAN.md`). Другие шаги не трогай, лишнего не добавляй. Заметил улучшение вне шага, предложи в конце отчёта.
4. Не удаляй и не переписывай файлы пользователя без просьбы. Файлы спецификаций `PLAN.md`, `docs/tasks/`, `docs/reference/` и `docs/OPEN_QUESTIONS.md` не редактируй без прямой просьбы пользователя (нашёл ошибку — сообщи). В `PROGRESS.md` меняй только отметки и «Журнал».

## Как выполнять шаг

1. Найди задачу `Txx` в `PLAN.md` и открой только соответствующий файл `docs/tasks/Txx.md`. Прочитай **только те справочники R1–R10, которые прямо перечислены в строке «Читать» этой задачи**, и только нужные подразделы. Не загружай все справочники целиком. Если задача ссылается на конкретный подраздел (например, R6 «Окна»), найди его в соответствующем файле и прочитай только этот подраздел. Если нужного подраздела/значения нет или источники конфликтуют, проверь `docs/OPEN_QUESTIONS.md` и спроси пользователя, не угадывай.
2. Посмотри `PROGRESS.md`: шаги из «Зависит от» должны быть отмечены сделанными. Если нет, скажи пользователю и остановись.
3. Сделай только текущий шаг. Если не описан технический способ реализации, но требования и игровой результат однозначны, выбери минимальное разумное решение и запиши его в «Журнал» под пометкой «решение». Если не хватает данных о механике, балансе, продуктовых правилах или есть конфликт источников — не выбирай сам, задай пользователю вопрос и остановись.
4. Проверь: `python tools/check.py` (после T04 также `python tools/test.py`, после T20 также `python tools/check_loc.py`). Если Godot доступен, `godot --headless --path . --quit` не должен печатать ошибок разбора скриптов.
5. Отметь шаг `[x]` в `PROGRESS.md`, допиши 1-3 строки в «Журнал» (что сделано, что осталось непроверенным).
6. Напиши отчёт пользователю: что сделано; что проверено; **что не проверено**; что проверить ему руками (скопируй пункт «Тебе проверить» из шага). Закончи фразой: «Если всё в порядке, напиши «фиксируй»».
7. Жди ответа. Нашёл проблему, исправляй в этом же шаге и не переходи к следующему.
8. Папка проекта и путь к Godot лежат в `CLAUDE.local.md` (не в репозитории). Если файла нет — спроси владельца. Godot можно задать переменной `GODOT_BIN`.

## Каркас: не ломать

Каркас: `autoload/ya.gd`, `autoload/save.gd`, `autoload/loc.gd`, `web/shell.html`, `export_presets.cfg`, `project.godot` (рендер, существующие автозагрузки), `tools/`.

- Менять каркас можно только там, где шаг прямо разрешает (например, добавить ключи в `Loc.T`, поля в `Save.DEFAULTS`, строку в `[autoload]`). Иначе остановись и объясни, зачем нужна правка.
- Весь доступ к SDK только через `Ya`. `JavaScriptBridge` разрешён только в `autoload/ya.gd`, слова `YaGames` и `ysdk` только в `web/shell.html`. Новые возможности SDK не придумывай по памяти: найди актуальную документацию Яндекса и добавь по образцу (JS-мост, затем `Ya._on_js_event`, затем метод `Ya` с заглушкой для редактора).
- Порядок старта: `await Ya.initialize()`, `await Save.load_all()`, `Game.start()` (после T03), `Ya.loading_ready()`, `Ya.gameplay_start()`.
- Новые автозагрузки не добавляй, кроме `Game` в шаге T03.

## Как пользоваться каркасом

```gdscript
Ya.show_interstitial()                      # только в паузах; частоту ограничивает сам Ya
Ya.show_rewarded(func(): ...)               # награда только внутри колбэка, по кнопке игрока
Ya.gameplay_start() / Ya.gameplay_stop()    # когда игра идёт / на паузе, в меню, в окнах
Ya.submit_score("имя_лидерборда", число)
Save.data["поле"]; Save.save_data()         # поля описаны в Save.DEFAULTS, сохранять по событиям
Loc.t("ключ")                               # тексты в Loc.T, минимум ru и en
```

Во время рекламы дерево сцены на паузе и звук выключен. Не ставь `process_mode = ALWAYS` на игровую логику. Вне Яндекса (редактор) `Ya` работает заглушкой: реклама имитируется, награда выдаётся сразу.

## Правила кода и платформы

- Рендерер только `gl_compatibility`, веб без потоков. Нельзя: `Thread`, `Semaphore`, `OS.execute`, `OS.delay_msec`, GDExtension, C#. `get_tree().quit()` в вебе ничего не делает. Плагины и библиотеки без согласия не добавлять.
- Типизация везде, где можно. `snake_case` для функций и переменных, `PascalCase` для классов и узлов, `UPPER_SNAKE` для констант. Связь через сигналы, узлы через `@onready`, без длинных `get_node("../../...")`. Один файл, одна ответственность.
- В `_process` нет создания объектов. Повторно используй (пул).
- Видимый текст только через `Loc.t("ключ")`, ключи в `Loc.T` на ru и en. Хардкод строк в интерфейсе запрещён. При `Loc.language_changed` тексты обновляются.
- Сохранения только через `Save`: только JSON-типы (int, float, String, bool, Array, Dictionary). После загрузки числа в массивах приходят как `float`, приводи `int(...)`. Не сохраняй каждый кадр. Поля не удалять и не переименовывать без миграции.
- Числа и таблицы баланса лежат в `scripts/data/`, формулы в `scripts/logic/` (без узлов), сцены только отображают. Нигде больше эти числа не дублируются.
- Реклама: rewarded только по явной кнопке игрока, interstitial только в естественных паузах (не на старте, не посреди действия, не сразу после rewarded).
- Не угадывай API Godot, если не уверен в имени или сигнатуре: проверь в документации Godot 4 (поиск в вебе) или в уже написанном рабочем коде. Не смог проверить, так и скажи в отчёте.

## Мобильность

- Основной сценарий: телефон, один палец. Кнопки не меньше 64x64 пикселя в базовом разрешении 1280x720. Нет hover, правой кнопки мыши и клавиатуры как единственного способа что-то сделать.
- Интерфейс на `Control` с якорями и контейнерами, не абсолютными координатами.
- Игровые действия через собственный `InputRouter` (шаг T07), в `project.godot` действия не добавлять, создавать в коде через `InputMap.add_action`.

## Правила для 3D (в проекте включено: `docs/budget.json`, `allow_3d`)

- Тени выключены. Один `DirectionalLight3D` и мягкий окружающий свет через `WorldEnvironment`, туман можно. Нельзя `OmniLight3D`, `SpotLight3D`, SSAO, SSR, SDFGI, объёмный туман, glow, `GPUParticles3D` (только небольшие `CPUParticles3D`) и `ShaderMaterial` без явной просьбы.
- Мир из примитивов, один материал на цвет. Повторяющиеся предметы (больше десятка) через `MultiMeshInstance3D`. В кадре не больше 100 `MeshInstance3D` и около 150 тысяч треугольников.
- Звери (T24d/T24f): три режима. Режим А это один `MeshInstance3D` на зверя (запасной, по умолчанию в руках). «Лёгкий» режим для зверей загона: не больше 3 `MeshInstance3D` на зверя (корпус и две пары ног, у безногих корпус и две части волны). «Полный» режим: до 12 `MeshInstance3D`, только один такой зверь в кадре (экран получения). Лимит 100 `MeshInstance3D` в кадре действует и на загон: 20 зверей по 3 части это 60. Мир и звери в сумме не должны его превышать. Один материал на зверя, меши строятся один раз при показе, не в `_process`.
- Модели `.glb`: один материал, текстура не больше 512x512, до 3000-5000 треугольников, загружать по требованию через `ResourceLoader`. Нет файла модели, показывай заглушку из примитива, а не ошибку.
- Физику не используй, если можно обойтись: движение и границы кодом по `delta`.
- Закрытым окнам и неиспользуемым объектам выключай обработку (`set_process(false)`) или убирай из дерева.
- Картинки: lossy WebP там, где можно. Звук: OGG, музыка с низким битрейтом.

## Релизный чек-лист (шаг T29)

- `python tools/build.py` проходит, размер архива записан и сравнён с прошлой сборкой.
- Проверено на телефоне: нет скролла страницы и случайного зума, касания работают.
- Нет ошибок в консоли браузера. Языки ru и en заполнены.
- Rewarded выдаёт награду только после просмотра, interstitial не мешает старту.
- Лидерборд `best_throw` создан в консоли разработчика, отправка рекорда проверена.
- Актуальные требования модерации Яндекса перечитаны в консоли, а не взяты из памяти.

## 9. Итоговый отчёт

Короткий, в таком виде:

1. **Что сделано.**
2. **Изменённые файлы.**
3. **Что проверено** (команды и фактические результаты) и **что не проверено**.
4. **Что осталось или вызывает сомнения.** Если ничего, напиши «нет».
5. **Что пользователю стоит посмотреть самому.**

Задача считается законченной только тогда, когда сделано то, что просили, ничего лишнего не сломано, проверки выполнены, а отчёт совпадает с реальными действиями. Если одно из условий не выполнено, так и пиши.

Когда закончил задачу или остановился с вопросом, последним действием выполни `powershell -ExecutionPolicy Bypass -File tools\notify.ps1 "Готово: <название задачи>"`. Кроме этого и команд git push/git pull по слову «фиксируй», код и скрипты в сеть не обращаются

## Dual Repository Setup (два GitHub репозитория)

Проект синхронизируется с **двумя удалёнными репозиториями**:

| Remote | URL | Аккаунт | Назначение |
|--------|-----|---------|------------|
| `origin` | `https://github.com/sesterinv-dev/feed-the-animals-2.git` | `sesterinv-dev` | Основной репозиторий |
| `origin2` | `https://github.com/morrowelias9-create/feed-the-animals.git` | `morrowelias9-create` | Копия / зеркало |

### Как пушить в оба репозитория

**Вариант А — по очереди (рекомендуется, надежнее):**
```bash
git push origin main && git push origin2 main
```

**Вариант Б — одной командой через pushurl (настроить разово):**
```bash
git remote set-url --add --push origin https://github.com/morrowelias9-create/feed-the-animals.git
# Теперь просто:
git push origin main  # пойдёт в оба
```

### Важные нюансы

1. **Авторизация:** `origin2` доступен аккаунту `sesterinv-dev` через *Collaborator* доступ (Settings → Collaborators → Add people → `sesterinv-dev` с ролью Write). Никаких токенов/SSH для второго аккаунта не нужно.

2. **Разные истории:** Репозитории **не являются форками** друг друга (имеют разные истории коммитов). При первом пуше в `origin2` и при расхождении историй потребуется **force push**:
   ```bash
   git push origin2 main --force
   ```
   Используй `--force` только для `origin2`, для `origin` — обычный пуш. **Принудительный push в origin2 делай только по отдельной просьбе пользователя.**

3. **Правило для агента:** При команде пользователя «фиксируй»:
   - Сделай обычный коммит и пуш в `origin main`
   - Затем пуш в `origin2 main` (с `--force` **только по отдельной просьбе пользователя**, сообщи пользователю)
   - Проверь `git status` и `git log origin/main..HEAD` для обоих remote

4. **Если `origin2` отклоняет пуш (non-fast-forward):**
   - Сделай `git pull origin2 main --rebase` — если конфликтов мало, реши их
   - Если конфликтов много (разные истории) — `git rebase --abort` и `git push origin2 main --force` (только по просьбе)

5. **GitHub Actions / CI:** Если настроены — они сработают в обоих репозиториях при пуше.
